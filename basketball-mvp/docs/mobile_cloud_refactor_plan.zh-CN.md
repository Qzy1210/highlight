# 移动端与云服务重构计划（基于 gin_fram 风格）

## 1. 目标

将当前以桌面调试为主的 `app-go` 重构为“双形态”架构：

1. `Desktop` 形态：保留现有 macOS 桌面应用（本地 HTTP + WebView）。
2. `Cloud API` 形态：新增前后端分离、可部署到云服务器的标准 HTTP 服务，供移动端 APP 调用。

并补齐登录鉴权与多用户任务隔离能力。

## 2. 架构原则（最佳实践）

1. 同一套业务能力，两个运行形态共享核心逻辑。
2. API 首先标准化，再做客户端适配，避免协议分叉。
3. 认证与授权前置，所有任务接口默认用户隔离。
4. 渐进式迁移：先建新骨架与核心接口，再逐步迁移旧接口。
5. 桌面端继续走 HTTP 调用，不走直接函数调用。

## 3. 迁移范围

### 3.1 保留

1. 现有 `cmd/desktop`（桌面壳）保留。
2. 现有检测/剪辑核心逻辑（`engine`/`pipeline`/`ffmpeg`）保留。

### 3.2 新增

1. 新 API 服务入口（云部署）。
2. gin_fram 风格分层：`router -> controller -> logic -> repository`。
3. 认证模块：登录、令牌、鉴权中间件。
4. 多用户隔离：任务与查询强制按 `user_id` 过滤。

### 3.3 改造

1. 任务模型补充 `user_id`。
2. 任务相关接口统一在鉴权下运行。
3. 桌面端调用方式改为配置化 API 基址（本地/远程可切换）。

## 4. 分阶段计划

## Phase A：架构与协议冻结（1-2 天）

1. 完成 API 协议草案（鉴权、任务、状态、导出）。
2. 定义统一响应体与错误码。
3. 定义桌面端兼容策略（默认本地，支持远程 API）。

产出：

1. `API 草案文档`
2. `错误码与鉴权说明`
3. `迁移清单`

## Phase B：云端骨架搭建（2-3 天）

1. 新增云端服务入口（gin_fram 风格中间件链）。
2. 建立模块骨架：`controller/logic/repository/model/router`。
3. 引入配置管理与启动参数（端口、密钥、存储路径）。

产出：

1. 可启动的 API 服务（`/health` 可用）
2. 基础路由分组（`/api/v1`）

## Phase C：登录鉴权模块（2-3 天）

1. 账号模型（先支持本地存储，后续可切 MySQL）。
2. 登录接口（密码校验、签发 Access/Refresh）。
3. 鉴权中间件（解析 JWT、注入 user context）。

产出：

1. `POST /api/v1/auth/login`
2. `GET /api/v1/auth/me`
3. 刷新令牌与退出接口（可选首版）

## Phase D：任务隔离与核心任务接口迁移（4-6 天）

1. 任务模型增加 `user_id`。
2. 创建任务、查询任务、终止任务按用户隔离。
3. 迁移关键接口：`single-job/start`、`jobs/:id`、`jobs/:id/terminate`、`jobs/:id/reexport`。

产出：

1. 多用户隔离生效（跨用户不可见）
2. 移动端可用任务全流程

## Phase E：桌面端兼容改造（2-3 天）

1. 桌面端新增 API 基址配置（默认 `http://127.0.0.1:8088`）。
2. 本地模式与云端模式统一走 HTTP 协议。
3. 保留文件选择与本地预览能力（桌面特有接口单独分组）。

产出：

1. 桌面端可切换本地/远程 API
2. 不破坏现有桌面使用体验

## Phase F：上线准备（2-4 天）

1. 部署脚本（Docker/systemd）与环境变量模板。
2. 日志、超时、并发与限流策略。
3. 安全策略（密码哈希、令牌失效、审计日志）。

产出：

1. 可上云部署包
2. 发布说明与回滚方案

## 5. 鉴权与隔离设计（首版）

## 5.1 鉴权

1. 登录：用户名+密码。
2. 密码存储：`bcrypt` 哈希。
3. 令牌：`JWT Access Token`（短时）+ `Refresh Token`（长时）。
4. 中间件：校验 JWT 后将 `user_id` 写入上下文。

## 5.2 隔离

1. 任务创建时写入 `user_id`。
2. 任务查询、更新、终止均加 `WHERE user_id = current_user_id`。
3. 响应中不暴露其他用户资源路径。

## 6. 接口建议（首批）

1. `POST /api/v1/auth/login`
2. `GET /api/v1/auth/me`
3. `POST /api/v1/jobs`
4. `GET /api/v1/jobs/:id`
5. `POST /api/v1/jobs/:id/terminate`
6. `PUT /api/v1/jobs/:id/events`
7. `POST /api/v1/jobs/:id/reexport`

## 7. 风险与规避

1. 风险：一次性迁移过大导致桌面回归风险。
   - 规避：保留旧入口，采用“新服务并行 + 逐接口迁移”。
2. 风险：视频文件在云端存储成本与传输成本高。
   - 规避：首版保留本地桌面高性能路径，云端重点服务移动端上传场景。
3. 风险：任务中断不彻底。
   - 规避：统一 `context cancel` 传递到 Python 与 ffmpeg 进程。

## 8. 验收标准

1. 移动端可完成登录、创建任务、查询任务、终止任务。
2. 不同用户互不可见任务。
3. 桌面端默认模式不受影响。
4. 新服务可在云服务器部署并稳定运行。
